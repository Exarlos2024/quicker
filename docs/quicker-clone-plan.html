复刻 Quicker：快速启动面板的最小可行方案

拆解 Quicker 的核心交互，梳理 Windows 平台实现这类工具的全部技术难点，给出可落地的架构与分阶段路线。

目标功能边界：全局快捷键唤出面板 · 面板内添加/启动 应用·文件夹·文件 · 基本增删改与搜索

结论速览

你要做的这个东西，本质上是四件事的组合：一个常驻托盘的后台进程 + 一个全局热键监听器 + 一个置顶无边框的网格面板 + 一个「路径 → 图标 → Shell 启动」的执行层。

技术难度不高，但有 8 个 Windows 平台特有的坑，几乎每一个都会让新手卡住半天到一天。这些坑（前台焦点锁、图标句柄泄漏、网络路径卡死、单实例、热键冲突）才是这个项目真正的成本所在，而不是 UI。

推荐栈：C# WPF + .NET 8。理由：Quicker 本身就是 .NET 技术栈，Win32 API 调用最顺，启动快、内存低（30–60MB，Electron 要 150MB+），图标/热键/托盘全部原生支持。

Rust 是第二条可行路线，而且不差——用 Tauri 2 可以做到 5–10MB 体积、UI 用 HTML/CSS 自由发挥，已经有 ReFast、一点 OnePoint 这样的成熟先例（详见第五节）。代价是图标提取要手写 FFI，以及编译慢会拖累 UI 调优的节奏。若只想 1 小时内看到能跑的原型，用 Python + PySide6，代码量能少一半。

一、Quicker 是怎么工作的

先把产品拆开看。Quicker 官方文档里有一句话精准概括了它的核心循环：

选择要操作的对象 → 弹出面板 → 选择动作 → 自动关闭

这个「四步循环」就是它的灵魂。面板不是常驻的，而是瞬时唤出、用完即走的。理解这一点，才能理解后面所有的设计取舍——比如为什么面板必须抢键盘焦点、为什么执行完动作要立刻隐藏。

面板的物理结构

Quicker 的面板窗口由四个区域构成，从上到下：

  • 标题栏：设置、钉住（Pin）、菜单、关闭。钉住后面板不再自动隐藏，用于连续操作。
  • 全局面板区：不随前台程序切换，放跨场景通用的动作。
  • 上下文面板区：随当前前台窗口自动切换。在 Chrome 里显示 Chrome 的动作页，在 VS Code 里显示 VS Code 的。没配置过场景的软件，回落到「通用」动作页。
  • 腰栏：当前动作页名、翻页指示点、搜索、锁定（暂停自动切换）、工具箱。

面板是网格布局的——不是列表。默认一行 5 个格子，动作以图标+文字的形式排布，鼠标滚轮翻页。这跟「搜索式启动器」（PowerToys Run / Flow Launcher 那种一条输入框）是完全不同的交互哲学：网格靠肌肉记忆，搜索靠打字。

触发与关闭

唤出方式
  • 鼠标中键点击
  • 单击 Ctrl 键（Quicker 的招牌）
  • 全局快捷键组合
  • 按住鼠标键滑动 / 触发浮标
关闭方式
  • 执行完一个动作后自动隐藏
  • 点击面板外部任意位置
  • 按 ESC / 再按一次中键
  • 点右上角 ×

注意「单击 Ctrl 唤出」和「点击面板外部隐藏」这两条——它们决定了必须用底层键盘/鼠标钩子（Hook），而不是 RegisterHotKey，因为 RegisterHotKey 无法注册「单个 Ctrl 键」这种无修饰键的操作，也无法监听全局鼠标点击。这是选型上的第一个分水岭。

三、八个必须提前知道的坑

这一节是整份报告最有价值的部分。下面每一条，都是我基于 Windows 平台机制推演出的、这类工具绕不开的问题。

1
前台焦点锁：SetForegroundWindow 会静默失败

Windows 有一条「前台窗口锁定」策略：如果一个进程当前不在前台，它调用 SetForegroundWindow 只会让任务栏图标闪烁，而不会真的把窗口拉到前台。这是为了防恶意弹窗。你的热键是在后台进程里按下的，所以面板弹出来很可能拿不到键盘焦点——用户一打字，字跑到别的窗口去了。

解决：把自己的线程 AttachThreadInput 到当前前台窗口的线程，调用 SetForegroundWindow，再 detach；或临时把窗口设成 TopMost 后立刻复位。这是最经典的绕法。
2
图标句柄泄漏：GDI 对象涨到 1 万就崩

SHGetFileInfo 返回的 HICON 是非托管资源，转成 WPF 的 BitmapSource 后如果忘记 DestroyIcon，每个图标泄漏一个 GDI 句柄。Windows 单进程 GDI 句柄上限约 1 万，一个面板几百个图标来回刷新，很快就炸。

解决：转换完成后立即 DestroyIcon；并且必须做图标缓存（key = 路径 + 文件修改时间），磁盘缓存到本地目录。Quicker 专门有个「图标缓存」目录就是干这个的。
3
网络路径会让 UI 卡死数秒

如果添加的是网络共享（\\server\share\...）或已断开的移动硬盘上的文件，SHGetFileInfo 会同步等待超时，最长可卡 30 秒，而它是在 UI 线程调用的——面板直接假死。

解决：图标提取全部丢到后台线程池异步做，先显示占位图标，提取完再刷新；对文件夹用 SHGFI_USEFILEATTRIBUTES 直接取通用文件夹图标，不实际访问磁盘。
4
UseShellExecute=false 会让 .lnk / .url 打不开

用 Process.Start(path) 启动快捷方式时，如果 ProcessStartInfo 的 UseShellExecute 是 false，.lnk 会被当成二进制文件直接执行，报错或什么都不发生。必须设成 true，让它走 Windows Shell 的文件关联。

解决：统一 new ProcessStartInfo(path){ UseShellExecute = true, WorkingDirectory = dir }。「以管理员运行」则改 Verb = "runas"。
5
热键注册冲突：RegisterHotKey 返回 false 不代表你的代码错了

别的软件已经占用了同一个组合键（比如微信占 Alt+A，输入法占 Ctrl+Space），你的注册就会失败。而且失败是静默的，用户按了没反应，你会以为是代码 bug。

解决：注册失败时弹提示让用户换键；把「是否注册成功」作为设置界面的一等状态显示出来。默认键建议用冷门组合，如 Alt+Space 已可能被占用，用 Ctrl+Alt+Q 更稳。
6
底层钩子会被杀软误报、被系统超时踢掉

要实现「单击 Ctrl 唤出」，必须装 WH_KEYBOARD_LL 低级键盘钩子。这类钩子（连同 WH_MOUSE_LL）是键盘记录器的标准技术，大概率会被 Windows Defender 或国产杀软拦截/报毒。另外系统有 LowLevelHooksTimeout（默认 300ms），钩子回调里做耗时操作会被系统摘掉。

解决：钩子回调里只做「记录状态 + PostMessage」，绝不做实际业务；需要数字签名才能减轻误报。MVP 阶段建议先用 RegisterHotKey 绕开整个问题。
7
多显示器 + 高 DPI 下坐标全乱

用户有 2 个不同缩放比的显示器（比如主屏 150%、副屏 100%）时，Cursor.Position 拿到的是物理像素，而 WPF 用的是逻辑单位，面板会弹到错误的位置甚至屏幕外。

解决：用 GetCursorPos 拿物理坐标 → 用 MonitorFromPoint + GetDpiForMonitor 拿到该屏幕的 DPI → 换算后再定位。WinForms 的 Screen.FromPoint 也能帮忙，但 DPI 仍需单独处理。
8
单实例：用户双击两次图标会开出两个进程

两个实例意味着两套托盘图标、两次热键注册（第二次必然失败）、两份配置互相覆盖。

解决：命名 Mutex 做单实例检测；第二个实例通过命名管道（NamedPipeServerStream）向第一个实例发一条「唤出面板」消息，然后自己退出。

换个语言，这 8 个坑能省掉多少？

直接回答一个常见疑问：C# 的坑会更少吗？答案是——坑的总数不会少，但每个坑的填坑成本低很多。因为这 8 条里有一半是 Win32 机制层面的问题，跟语言无关；真正拉开差距的是「有没有现成封装可以直接抄」。

八个坑C# / WPFRust / Tauri
① 前台焦点锁 中 要写 AttachThreadInput，但现成答案极多 中 同样要写，且要手搓 FFI 签名
② 图标提取 易 两行：SHGetFileInfo + CreateBitmapSourceFromHIcon 难 GetIconInfo → DIB → DrawIconEx → 读像素，5 个资源手动释放
③ 网络路径卡死 易 async/await 成熟，后台线程池顺手 中 spawn_blocking 可用，但要注意 COM 线程模型
④ .lnk 打不开 易 UseShellExecute 默认就是 true 中 opener 够用，但 runas verb 要自己调
⑤ 热键冲突 易 封装库多，能拿到失败原因 易 global-hotkey 已封装
⑥ 钩子超时 / 杀软误报 难 无签名 .NET + 键盘钩子，误报率偏高 难 一样难，回调还要跨 FFI 边界
⑦ 多屏 DPI 中 Screen API + PerMonitorV2 有成熟做法 中 要自己算 scale factor
⑧ 单实例 易 Mutex + 命名管道，示例满天飞 易 single-instance crate

合计：C# 是 5 易 2 中 1 难；Rust 是 2 易 4 中 2 难。差距集中在「图标提取」和「有没有现成封装」这两件事上——也就是「跟操作系统打交道」的那部分成本，.NET 的 BCL 和 WPF 已经替你付了 20 年。

但 C# 也有它自己的坑

公平起见，说几个只有 C# 路线上才会遇到、Rust 那边没有的问题：

  • 体积和冷启动：self-contained 单文件发布 60–150MB（不开 trimming / AOT），冷启动有 .NET 运行时加载开销。Rust 只有 5–10MB。这是 Rust 碾压 C# 的地方。
  • AllowsTransparency=True 会禁用硬件加速：WPF 做圆角 / 阴影无边框窗口的常规做法，代价是渲染退回软件层，面板滚动会掉帧、拖动会闪。这是 WPF 专属坑。
  • DPI 感知要在 app.manifest 里配：漏配或配错，整个面板在高分屏上就是糊的。
  • Deactivated 事件会误触发：经典 bug——做「失焦自动隐藏」时，点自己面板里的按钮也可能触发 Deactivated，面板当场消失。必须额外判断焦点是否仍在自己的窗口树内。
  • XAML 绑定错误是运行时静默失败：写错了不报错，只是界面上少个东西，调试起来很烦。

所以真正的取舍是：C# 用「更大的体积、更慢的冷启动、更啰嗦的 UI 写法」换「跟 Win32 打交道时的省心」；Rust 正好反过来——用「手写 FFI 的麻烦」换「更小的体积和更自由的 UI」。

推荐路径

如果目标只是先跑起来看效果、验证交互手感 → 用 Python + PySide6，一个下午能出可运行的 demo，之后再决定要不要迁移。

五、Rust 路线详解

结论先说：Rust 完全可行，而且对这个项目来说是个相当合理的选择。技术风险已经被别人趟平了——ReFast（基于 Tauri 2 的 Windows 快速启动器，MIT 协议）已经实现了全局热键、托盘、图标提取与缓存、Everything 集成、失去焦点自动关闭搜索框这一整套；一点 OnePoint 也是 Tauri 2 + Rust 写的键位启动器，默认 Alt+Space 唤出面板。

但必须说清楚一件事：第三节那 8 个坑，一个都不会消失。你只是把 C# 的 [DllImport] 换成了 Rust 的 FFI 绑定——该懂的 Win32 机制（前台焦点锁、HICON 释放、UseShellExecute、多屏 DPI）一点都不能少。

图标提取：Rust 路线最大的痛点

同一件事，对比一下两个语言的工作量。C# 是这样，两行就完事：

var shfi = new SHFILEINFO();
SHGetFileInfo(path, 0, ref shfi, (uint)Marshal.SizeOf(shfi), SHGFI_ICON | SHGFI_LARGEICON);
return Imaging.CreateBitmapSourceFromHIcon(shfi.hIcon, IntPtr.Zero, BitmapSizeOptions.FromEmptyOptions());
// 转完 DestroyIcon 一调就收工

Rust 要这样（示意代码，省略了错误处理与 premultiply 细节）：

unsafe {
    let mut shfi: SHFILEINFO = std::mem::zeroed();
    SHGetFileInfoW(PCWSTR(wide.as_ptr()), FILE_ATTRIBUTE_NORMAL,
        Some(&mut shfi), size_of::<SHFILEINFO>() as u32,
        SHGFI_ICON | SHGFI_LARGEICON);

    // 1. HICON 本身不含像素数据，得先问系统要它的 bitmap
    let mut info: ICONINFO = std::mem::zeroed();
    GetIconInfo(shfi.hIcon, &mut info);

    // 2. 建一个 32 位带 alpha 的 DIB section 当画布
    let bmi = BITMAPINFO { bmiHeader: BITMAPINFOHEADER {
        biSize: size_of::<BITMAPINFOHEADER>() as u32,
        biWidth: w, biHeight: -h,        // 负高度 = 自上而下
        biPlanes: 1, biBitCount: 32, biCompression: BI_RGB.0, ..Default::default()
    }, ..Default::default() };
    let mut bits: *mut c_void = null_mut();
    let dc  = GetDC(None);
    let dib = CreateDIBSection(dc, &bmi, DIB_RGB_COLORS, &mut bits, None, 0);

    // 3. 把图标画到画布上
    DrawIconEx(dc, 0, 0, shfi.hIcon, w, h, 0, None, DI_NORMAL);

    // 4. 从 bits 读出 BGRA 像素，交给 image crate
    let px  = std::slice::from_raw_parts(bits as *const u8, (w * h * 4) as usize);
    let img = RgbaImage::from_raw(w as u32, h as u32, premultiply(px)).unwrap();

    // 5. 五个资源全部手动释放，漏一个就泄漏
    DeleteObject(dib);  ReleaseDC(None, dc);
    DeleteObject(info.hbmColor);  DeleteObject(info.hbmMask);
    DestroyIcon(shfi.hIcon);
}

ReFast 的作者在实现图标提取时，额外做了一套 PowerShell 兜底的提取方案，并加了「图标提取失败标记」避免重复尝试——这本身就是「原生 FFI 方案不够顺手」的信号。这是你选 Rust 前最该知道的一件事。

比 C# 强的地方
  • 体积 5–10MB、内存 30–80MB，比 Electron 低一半以上
  • UI 用 HTML/CSS 写，面板能做得比 WPF 好看得多，动效也容易
  • 内存安全，不用担心托管/非托管混用那类隐性 bug
  • 产物无运行时依赖（Tauri 需 WebView2，但 Win10/11 基本自带）
  • 跨平台潜力：同样的代码之后能出 macOS 版
比 C# 弱的地方
  • 图标提取没有干净的轮子，得自己写一套 HICON → RGBA
  • 编译慢：首次 3–10 分钟，增量改一行 30 秒–2 分钟。而这类工具最需要「反复调 UI 手感」，慢反馈会明显拖节奏
  • 所有 Win32 调用都要手写 FFI 签名，没有 C# 那种现成封装库
  • 低级键盘钩子的回调跨 FFI 边界，更容易踩到微妙的坑
Rust 路线的建议
  • 想要小体积 + 好看的 UI + 现代技术栈，不介意慢编译 → 选 Tauri 2，架构直接对着 ReFast 抄
  • 想要纯原生、极致轻量、零 WebView2 依赖 → 选 egui，但做好手写网格面板与图标渲染的准备
  • 只想最快跑通、最省心 → C# WPF 仍然是最优解（图标提取两行、无需 FFI）
  • 只想先验证交互手感 → Python + PySide6，一个下午出可运行 demo

提取文件图标（含释放与缓存）

[StructLayout(LayoutKind.Sequential, CharSet = CharSet.Unicode)]
struct SHFILEINFO { public IntPtr hIcon; public int iIcon;
  [MarshalAs(UnmanagedType.ByValTStr, SizeConst = 260)] public string szDisplayName;
  [MarshalAs(UnmanagedType.ByValTStr, SizeConst = 80)]  public string szTypeName; }

[DllImport("shell32.dll", CharSet = CharSet.Unicode)]
static extern IntPtr SHGetFileInfo(string pszPath, uint attr,
    ref SHFILEINFO psfi, uint cb, uint flags);

[DllImport("user32.dll")] static extern bool DestroyIcon(IntPtr hIcon);

BitmapSource GetIcon(string path) {
    var shfi = new SHFILEINFO();
    SHGetFileInfo(path, 0, ref shfi, (uint)Marshal.SizeOf(shfi),
        SHGFI_ICON | SHGFI_LARGEICON);          // 0x100 | 0x0
    try {
        return Imaging.CreateBitmapSourceFromHIcon(
            shfi.hIcon, IntPtr.Zero, BitmapSizeOptions.FromEmptyOptions());
    } finally {
        DestroyIcon(shfi.hIcon);                 // ← 漏掉这行必崩
    }
}

强制把面板拉到前台（破解前台锁）

[DllImport("user32.dll")] static extern IntPtr GetForegroundWindow();
[DllImport("user32.dll")] static extern uint GetWindowThreadProcessId(IntPtr h, IntPtr pid);
[DllImport("user32.dll")] static extern bool AttachThreadInput(uint a, uint b, bool f);
[DllImport("user32.dll")] static extern bool SetForegroundWindow(IntPtr hWnd);

void ForceForeground(IntPtr myWnd) {
    var fg = GetForegroundWindow();
    uint fgThread = GetWindowThreadProcessId(fg, IntPtr.Zero);
    uint myThread = GetWindowThreadProcessId(myWnd, IntPtr.Zero);
    AttachThreadInput(myThread, fgThread, true);   // 挂到前台线程上
    SetForegroundWindow(myWnd);
    AttachThreadInput(myThread, fgThread, false);  // 立刻脱离
}

实现阶段新踩到的坑（原方案没预见到）

① 低级钩子的生命周期与误判。完整的五个坑（委托被 GC 回收、回调 300ms 超时被静默摘钩、自触发死循环、钩子线程、误判）写在项目 README.md 里。其中误判最花时间——难点不是识别 Ctrl，而是排除掉所有「按着 Ctrl 干别的事」：Ctrl+C、Ctrl+左键多选文件、Ctrl+滚轮缩放、先按住 Shift 再点 Ctrl、长时间按住 Ctrl 当修饰键。少排除任何一种，用户都会觉得这个功能在乱弹。

② 开始菜单的本地化目录联接。中文版 Windows 的开始菜单里同时存在「程序」和「Programs」，程序 是指向 Programs 的 junction。按路径字符串去重挡不住它——两个路径长得完全不一样，指向的却是同一批文件。第一版扫描器把 200 个快捷方式扫成了 353 个。修法是按目录的「真实身份」去重：DirectoryInfo.ResolveLinkTarget(returnFinalTarget: true) 把 junction 解析到最终目标，普通目录用自身 FullName，两者正好能撞上。

③ 内部拖拽和「拖文件进面板」会互相打架，而且下标数学比看上去脆弱。窗口级的 AllowDrop 只认 FileDrop，格子拖拽一进来就被判成「不支持的格式」——光标变成禁止符号，拖文件用的提示遮罩还会误亮。解法是用自定义剪贴板格式 QuickerLite.Tile 把两者区分开，并在格子区域的处理器里 e.Handled = true 截住事件，不让它冒泡到窗口级。
另外「松手应该插到第几位」这段数学有两个陷阱：面板是 WrapPanel 换行网格，只按最近距离算的话，在行尾的空白处松手会插到上一行去，正确做法是先按 Y 定位到行、再在行内按水平中线比较；往右拖时目标下标还要减一，因为被拖的格子会先被摘出去、它后面的下标全部前移一位，漏掉这一步的表现是「往右拖一格没反应，拖两格才动一格」。这段逻辑抽在 Core/TileReorder.cs 里做成纯函数，配了 44 条断言（./test.sh）——纯逻辑必须能脱离界面单独跑，这一点在扫描器那个 bug 上已经验证过一次了。多选之后又补了一条：块搬移的位移量只数「插入点之前的被移项」，不是选区总数；而且「有没有变化」不能用下标判断，不连续的选区（比如下标 0 和 9）可能算出跟原来一模一样的顺序，只能拿结果整表比较。
跨页拖拽又暴露了一个 WPF 事件顺序上的细节：窗口级的 AllowDrop 会把「拖到腰栏空白处」当成「移到末尾」，可拖拽期间腰栏已经变成页签区了，落空应该什么都不做。解法是给腰栏自己加一层 DragOver/Drop 并 e.Handled = true 截住它；同时用一个门闩 _dropModeActive 防止「落位回调」和「拖拽结束」两次恢复腰栏、把刚设好的状态提示冲掉。
